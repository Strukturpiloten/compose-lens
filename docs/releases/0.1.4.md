# ComposeLens 0.1.4

ComposeLens 0.1.4 promotes service dependencies into the native merged-project consumer view.
Converters can inspect effective multi-file dependency intent directly without rendering and
reparsing YAML or losing the source of nested options.

## Added

- `ProjectService::depends_on` exposes effective dependency entries after Compose-aware merge and
  optional explicit profile selection.
- `ProjectDependsOn` keeps sequence short syntax distinct from mapping long syntax.
- `ProjectServiceDependency` retains the service name plus optional `condition`, `restart`, and
  `required` values.
- The field, each dependency, each service-name key, and each nested option retain complete merge
  provenance.
- Interpolated semantic keys expose sensitivity and redact their values from `Debug` output.
- Unknown and extension options remain source-addressable through unmodeled field references.
- Malformed option maps, booleans, and conditions produce recoverable project-view diagnostics.

## Compatibility

The public changes are additive within the documented 0.1.x compatibility line. Existing callers
do not need to change. Rust 1.85.0 remains the minimum supported Rust version.

## Semantic boundary

Compose dependency conditions remain distinct. `service_started`, `service_healthy`, and
`service_completed_successfully` are not normalized into one ordering edge. Likewise, Compose's
`restart: true` describes restarts initiated by explicit Compose operations, not ordinary runtime
restart policy. Target adapters must report whether each behavior is exact, approximate,
unsupported, or invalid.

## Upgrade guidance

Consumers using `build_project_view` can read `ProjectService::depends_on` directly. Use the outer
and nested `ProjectValue` provenance when a conversion report must identify every contributing
Compose file.
