# ComposeLens 0.1.0 release candidate

Status: repository-ready; not yet published.

This is the first public ComposeLens library candidate. It establishes the supported 0.1.x API
line for BoxFerry and other tools that need loss-aware Compose processing without invoking a
provider or runtime.

## Included capabilities

- byte-preserving YAML syntax documents with source-aware diagnostics;
- the documented native Compose boundary, including distinct short and long forms, extra hosts,
  raw identities, ulimits, health checks, dependency conditions, container paths, and field-level
  build/deploy identities;
- tolerant `name:tag@digest` image references;
- explicit caller-owned interpolation, multi-file loading, merge, profile, path, reference, and
  default stages;
- exact-version compatibility reports backed by documentation and reviewed provider observations,
  including evidence-backed `host-gateway` and Podman user-namespace findings;
- deterministic canonical rendering and atomic scalar preservation edits; and
- a redistributable real-world corpus from Strukturpiloten TYPO3 and Docker Awesome Compose.

## Compatibility evidence

The release archive retains 48 reviewed provider-config records for Docker Compose 2.24.3, 2.24.4,
2.40.3, and 5.3.1 plus `podman-compose` 1.3.0 and 1.5.0. The exact result table is in
[provider-config conformance](../research/provider-config-conformance-2026-07-31.md).

Official Podman 5.4 documentation establishes runtime evidence for `host-gateway`, `keep-id`,
`auto`, and `nomap`. Compose-provider pass-through is still classified as unknown until an exact
conformance record exists.

The 36 SELinux runtime-effect entries are planned, not observed. They require exact Docker or
Podman runtimes, rootless and rootful isolation, a preloaded digest-pinned image, and an enforcing
SELinux host. Provider `config` acceptance is not presented as proof of a runtime relabel effect.

## Known limits

- The native model intentionally covers the first BoxFerry conversion boundary, not the complete
  Compose Specification.
- Structural preservation edits are not available; the supported editing boundary is exact
  scalar replacement.
- Runtime-effect matrix results are not yet available.
- No API beyond the documented 0.1.x contract carries a 1.x stability promise.

## Maintainer publication checklist

Publication is an external, credentialed operation and is intentionally separate from repository
implementation completion.

1. Review and commit a clean release tree.
2. Replace the changelog's unreleased heading with the release version and date.
3. Run every command in `docs/testing.md`, including `cargo deny check` and documentation checks.
4. Run `cargo package --locked` from the clean tree and inspect the archive file list.
5. Publish with the maintainer's crates.io credentials.
6. Create a signed or annotated `v0.1.0` tag at the published commit and push it.
7. Create the GitHub release from this document and link the crates.io and docs.rs pages.
8. Verify the published crate metadata, documentation, license, and repository links.

Do not move this document to released status merely because the package builds locally.
