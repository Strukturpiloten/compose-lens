# ComposeLens 0.1.14

ComposeLens 0.1.14 expands the source-compatible 0.1.x API with loss-aware native boundaries for
service lifecycle, identity, capability, device, and resource settings. The release carries each
supported field through authored documents, effective multi-file projects, deterministic
generation where a safe construction contract is available, and the evidence needed to explain
non-exact downstream decisions.

## Lifecycle and service identity

- A distinct `Entrypoint` model retains null, scalar, list, and explicitly empty forms, while
  `GeneratedEntrypoint` writes deterministic parse-back-validated output.
- Service `init` retains omission, literal and deferred authored values, and complete replacement
  provenance. Generated construction accepts only an explicit boolean and never invents a default.
- Independent `stop_signal` and `stop_grace_period` values retain raw spelling, deferred or invalid
  states, sensitivity, and replacement provenance. Generation keeps caller-selected signal text
  and validates grace periods against ComposeLens's documented-unit policy without converting
  them to another lifecycle manager's units.
- `pull_policy` retains documented policies, the `if_not_present` alias, custom intervals,
  deferred values, schema-only `refresh`, and provider-specific evidence. Generated construction
  emits only the documented safe subset; `pull_refresh_after` remains source-addressable evidence.
- Service `hostname` retains resolved, deferred, and invalid authored literals without
  synthesizing a name. Generated hostnames use conservative ASCII RFC-1123 validation.

## Resource and container settings

- `pids_limit` retains unlimited, arbitrary-precision finite, lexical-zero, deferred, and other
  spellings. Generated output accepts only unlimited or positive integral values.
- `shm_size` and `mem_limit` retain exact scalar text, YAML kind, documented lowercase-unit
  classification, lexical zero, deferred expressions, provider-dependent values, sensitivity,
  and multi-file replacement provenance. Generated values require a canonical positive ASCII
  amount plus an explicit Compose-owned unit and never inject defaults.
- Service-level `tmpfs` retains scalar or list form, explicit empty lists, ordered duplicates,
  raw target options, interpolation sensitivity, reset/override behavior, and merge provenance.
- `sysctls` retains mapping or list form, scalar spelling and kind, ordering, duplicates,
  sensitivity, generic collection merging, reset, and override. Generation emits resolved quoted
  strings without interpreting namespaces or kernel behavior.
- Effective and generated `ulimits` retain ordered names, scalar or soft/hard form, nested
  recursive-merge provenance, exact scalar spelling and kind, sensitivity, explicit empty/reset
  maps, replacement, and override. Generated values are limited to resolved `-1` or non-negative
  ASCII decimals.
- Independent `cap_add` and `cap_drop` boundaries retain omission versus explicit empty lists,
  exact-case ordering, duplicate evidence, sensitivity, and merge provenance. Generated values
  apply no capability whitelist or cross-field reconciliation.
- Service `devices` retains ordered mixed short and long forms, including raw path, CDI-like,
  deferred, and opaque short values plus long-form source, target, permissions, extensions,
  unknown fields, nested provenance, sensitivity, reset, and override. Existing target-keyed merge
  semantics remain visible; generated construction validates only safe resolved strings.

## Compatibility and API boundary

These additions are additive and source-compatible under the documented ComposeLens 0.1.x policy.
Rust 1.85.0 remains the minimum supported version. Public APIs continue to use ComposeLens-owned
types, keep the YAML backend private, preserve stable diagnostic codes, and keep parsing,
interpolation, merging, project views, validation, and rendering as explicit side-effect-free
stages. Successful generated documents are reparsed through both the syntax and native model
layers before being returned.

Provider-config entries added for these fields remain planned evidence questions until exact
observations are captured and reviewed. ComposeLens does not inspect host devices, memory, cgroups,
namespaces, capabilities, mounts, kernels, or runtime state; it does not claim provider enforcement
or translate values into Quadlet, Podman, systemd, or another target format. Runtime policy and
cross-format exactness remain responsibilities of the consuming application and its selected
target profile.
